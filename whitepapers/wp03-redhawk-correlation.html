GridStack vs. RedHawk-SC on real chip designs

AbstractBenchmark grids show that a solver is fast. A sign-off team needs to know whether it gives the same answer as the tool they already trust, on a real design. This paper runs GridStack 1.5 side by side with RedHawk-SC, run in-design from Synopsys Fusion Compiler, on two chips taken through place, route and sign-off in the SAED32 process: a RISC processor core with four SRAM macros, and a Groq-style LPU accelerator with eighteen SRAM macros and a 242K-node power grid. Both tools analyse the same grid, taps and per-cell power. Across static and dynamic analysis on both designs, GridStack's worst-case IR drop agrees with RedHawk-SC within 0.6–1.6%, and it completes the analysis 3.8–11× faster for dynamic IR drop and 23–27× faster for static IR drop.
3.8–27×faster than RedHawk-SC end to end: 3.8–11× dynamic, 23–27× static
≤ 1.6%difference in worst-case IR drop across all four analyses; 0.6–1.5% in three of them
242Kpower-grid nodes and 24,038 cells on the larger of two signed-off designs

1 / THE QUESTION

Does it agree with the sign-off tool, on a real chip?

Speed against a direct solver says nothing about agreement with the tool a sign-off flow is built on.

The IBM benchmarks in GS-WP-01 fix the grid and the stimulus and compare solvers. A production flow asks a harder question. Given a design that has been placed, routed and signed off, with real standard cells, SRAM macros, a power mesh designed for that floorplan and a vectorless activity model, does GridStack report the same IR drop at the same cells as RedHawk-SC?

To answer it, both tools were run on the same two designs, on the same server, from the same Fusion Compiler database. Every cell's result is compared one to one.

2 / THE DESIGNS

Two signed-off SAED32 chips

Both designs were implemented end to end in Synopsys Fusion Compiler: synthesis, floorplan and power mesh, placement, clock tree, routing and sign-off.

RISC_CORE is a compact processor core whose register files are SRAM macros. The LPU is a statically scheduled machine-learning accelerator in the style of Groq's tensor streaming processor: an 8 × 8 systolic matrix unit, a vector unit and an instruction sequencer, fed by sixteen SRAM data banks and two instruction-memory SRAMs.

The power grids

Both grids follow the same plan: M1 rails along every standard-cell row, M2 straps over the logic, and a mesh of horizontal M7 and vertical M8 straps over the whole die, joined by stacked vias. Supply enters through ideal taps at the ends of the M8 straps. Table 2 gives the grid that both tools analysed.

3 / METHOD

Same design, same inputs, cell-by-cell comparison

The comparison removes every difference except the analysis itself.

Sign-off database

Fusion Compiler opens the signed-off block. RedHawk-SC runs in-design, with vectorless activity, the SAED32 Cmax interconnect technology and the design's own liberty files.

Shared grid and stimulus

The DEF, LEF, tap locations, timing windows and parasitics that Fusion Compiler hands to RedHawk-SC are converted to a GridStack netlist, with resistances from the same technology file and per-cell power and current from the same analysis.

Cell-by-cell comparison

Both tools report the effective drop, VDD minus VSS, at every cell's power pins. Each cell is matched by name and compared, along with the worst cell and the top-50 list.

  • Static IR drop — each cell draws its average power divided by the supply voltage as a DC current between its VDD and VSS rails.
  • Dynamic IR drop, LPU — GridStack uses RedHawk-SC's own per-cell demand-current waveforms and cell decoupling capacitance, imported from the in-design run, plus the grid capacitance RedHawk-SC reports.
  • Dynamic IR drop, RISC_CORE — GridStack uses a vectorless switching model built from RedHawk-SC's per-cell power and Fusion Compiler's clock arrival times and switching windows, with a cell decoupling capacitance of 2 fF per cell.
All results use GridStack's sign-off mode: a full-order back-Euler transient over every grid node, with no model reduction. GridStack also provides a fast mode, the reduced-order Krylov engine of GS-WP-01, for rapid what-if evaluation during floorplanning and decap planning.

4 / ACCURACY

Worst-case drop within 1.6%, on every analysis

The two tools find the same worst-case IR drop, at the same cells.

In static analysis the two tools agree to within 0.6% on RISC_CORE and 1.5% on the LPU, with per-cell correlation of 1.000 and 0.9998. Both name the same worst cell on RISC_CORE, and their top-50 lists are identical. With RedHawk-SC's own current waveforms, the LPU's dynamic worst-case drop agrees to 1.5% and the per-cell correlation is 0.988. On RISC_CORE, whose dynamic stimulus is GridStack's own vectorless model, the worst-case drop agrees to 1.6% and 40 of the top 50 cells are shared; mid-range cells read higher because the two current models place switching events differently in time.

6 / TAKEAWAYS

Sign-off agreement at a fraction of the turnaround

On two real, signed-off designs, GridStack reproduces RedHawk-SC's IR-drop answer and returns it several times sooner.

  • Same answer. Worst-case effective IR drop within 0.6–1.6% of RedHawk-SC in static and dynamic analysis on both designs, with per-cell correlation of 0.948–1.000 and the same hotspots at the top of the list.
  • Sooner. Dynamic analysis 3.8–11× faster and static analysis 23–27× faster end to end, short enough to run IR drop on every floorplan or power-mesh iteration rather than once at the end.
  • From the existing flow. GridStack reads the same Fusion Compiler collateral that RedHawk-SC uses: DEF, LEF, tap locations, timing windows, parasitics and per-cell power. No separate extraction or layout database is needed.
  • Two modes. Sign-off mode for the numbers that go into a review; fast mode (GS-WP-01) for quick what-if sweeps, with results that can be viewed at die level as in GS-WP-02.
